# مدير اتصالات قواعد البيانات — المرحلة الأولى

## ما أُضيف

- سجل اتصالات منفصل في `config/database-profiles.json`، يحتوي بيانات التعريف فقط.
- كلمات مرور PostgreSQL وMySQL وMariaDB تحفظ عبر `SecretStore` في مخزن أسرار نظام التشغيل باستخدام مفتاح خاص بكل اتصال.
- واجهة سطح مكتب لإضافة الاتصالات وتعديلها واختبارها وتفعيلها وتعطيلها وحذف تعريف الاتصال.
- اختبار SQLite يفتح الملف الموجود بوضع القراءة فقط، ولا ينشئ ملفاً جديداً.
- فحص صحة MySQL/MariaDB يستخدم SELECT فقط على `information_schema` وجدول `files`، ويغلق الاتصال في جميع المسارات.
- اختبار PostgreSQL ينفذ `SELECT 1` فقط؛ لا ينشئ قاعدة بيانات أو جدولاً ولا يغير المخطط.
- موصل MySQL/MariaDB عبر PyMySQL ينفذ `SELECT 1`، مع مهلات اتصال/قراءة/كتابة محددة وكلمة مرور من مخزن أسرار النظام.
- يدعم MySQL/MariaDB إعداد TLS: تعطيل صريح، أو طلب TLS، أو التحقق من CA، أو التحقق من CA واسم المضيف. يتطلب `verify-ca` و`verify-full` ملف CA محدداً من الواجهة.
- لأن PyMySQL لا يقدم تفاوض TLS انتهازياً مطابقاً لـ libpq، فإن خيار `prefer` في هذا الموصل يطلب قناة TLS ولا يعد بالرجوع التلقائي إلى اتصال غير مشفر. خيارا `prefer` و`require` لا يتحققان من شهادة الخادم؛ استخدم `verify-ca` أو `verify-full` مع CA موثوق عند الحاجة للتحقق.
- أساس توجيه مستقل لكل مزوّد/نموذج/منتج، مع قاعدة افتراضية اختيارية.
- تعطيل/حذف اتصال مستخدم في التوجيه لا يؤدي إلى تحويل صامت إلى قاعدة أخرى. حذف التعريف لا يحذف قاعدة البيانات أو ملفات CSV/GRIB.

## ما لم يُنفذ بعد

1. ربط توجيه النماذج بمسارات كتابة بيانات الطقس الفعلية؛ المرحلة الحالية تحفظ قواعد التوجيه وتعرضها فقط.
2. توصيل MySQL وMariaDB بسجل تتبع التنزيلات فقط؛ أما توجيه بيانات الطقس ومزامنتها فما زالا مرحلة منفصلة.
3. نقل/نسخ بيانات بين قواعد متعددة، الدمج المركزي، إزالة التكرار، وتوثيق المصدر.
4. تقارير أحجام قواعد البيانات والملفات ومراقبة مزامنة المصادر.
5. تحويل الاتصال الحالي المستخدم لسجل التنزيلات إلى ملف تعريف مُدار تلقائياً؛ يبقى مسار SQLite/PostgreSQL الحالي كما هو حتى مرحلة ترحيل مستقلة مع نسخة احتياطية واختبارات مطابقة.

## ملفات البيانات

- `config/database-profiles.json`: أسماء الاتصالات ومضيفوها وقواعدها ومراجع مفاتيح الأسرار فقط.
- `config/database-routing.json`: تعيينات النموذج إلى معرّف ملف الاتصال فقط.
- لا تحفظ هذه الملفات كلمة مرور أو DSN يحتوي كلمة مرور.

## ضمانات السلامة

- لا تُنفذ هذه المرحلة أي ترحيل تلقائي ولا تكتب إلى قواعد بيانات المستخدم.
- لا تُحذف قاعدة SQLite الحالية أو قاعدة PostgreSQL الحالية عند حذف تعريف اتصال من الواجهة.
- يجب أن يسبق ربط أي مسار تنزيل جديد بقاعدة متعددة اختبار تكامل على قاعدة اختبار منفصلة، ثم اختبار ترحيل/استعادة قبل اعتماده.

## مؤشرات صحة قواعد البيانات — توسعة المرحلة الأولى

- أضيفت خدمة `database_health.py` لفحص SQLite وPostgreSQL في وضع القراءة فقط.
- تعرض الواجهة حالة الاتصال، وجود جدول تتبع الملفات، عدد السجلات، المكتمل والفاشل، الأحجام البعيدة والمحلية المسجلة، الحجم الفعلي لقاعدة البيانات، وآخر تحديث، لقواعد SQLite وPostgreSQL وMySQL وMariaDB.
- يجري الفحص في عامل خلفي حتى لا تتجمد الواجهة أثناء اتصالات الشبكة.
- لا تُنفذ الخدمة أي DDL أو DML، ولا تنشئ قاعدة أو جدولاً أو ملف SQLite.
- الأرقام المعروضة تخص جدول تتبع التنزيلات `files` فقط؛ لا تمثل عدد ملفات CSV/GRIB على القرص ولا حجم بيانات الطقس داخلها.
- أضيفت اختبارات لحساب الأعداد والأحجام، وغياب الملف/الجدول، وتعطيل الاتصال، والتأكد من عدم تغيير ملف SQLite.
- أضيف موصل PyMySQL واختبارات اتصال MySQL/MariaDB وفحص الصحة بوضع القراءة فقط، مع اختبار TLS وشهادة CA. لا يعني ذلك أن توجيه التنزيلات أو بيانات الطقس إلى هذه القواعد أصبح مفعّلاً.

## معالجة أمان حذف بيانات الاعتماد

إذا رفض مخزن أسرار نظام التشغيل حذف كلمة مرور اتصال، يبقى تعريف الاتصال. وإذا فشل حذف التعريف بعد إزالة كلمة المرور، يحاول البرنامج استعادة كلمة المرور من القيمة التي قرأها مسبقاً، مع اختبار انحدار لحالة فشل كتابة سجل الاتصالات.


## MySQL/MariaDB — حدود المرحلة الحالية

- ما أصبح متاحاً: حفظ ملف الاتصال، حفظ السر في مخزن النظام، اختبار الاتصال، فحص عدد سجلات `files` ومؤشراتها، وتحديد CA/التحقق من اسم المضيف.
- ما لم يصبح متاحاً بعد: توجيه تنزيلات ECMWF/GFS/ICON إلى MySQL، تحويل ملفات CSV/GRIB إلى جداول طقس، النسخ بين قواعد البيانات، والدمج المركزي.
- لا تنفذ هذه المرحلة ترحيلاً إلى MySQL أو تغييرات مخطط تلقائية، ولا تكتب أي صفوف اختبار إلى قاعدة خارجية.
- أضيف PyMySQL إلى تبعيات المشروع وملف PyInstaller حتى يدخل الموصل في الحزمة المحمولة.


## تشغيل التحقق يدوياً على أحدث رأس

لأن تشغيلات Windows السابقة أُلغيت أثناء تحديثات الفرع، ولأن بعض دفعات GitHub API قد لا تُنشئ تشغيل Actions تلقائياً، يجب التحقق من رأس الفرع الحالي عبر:

1. فتح تبويب Actions في المستودع.
2. اختيار **Python tests** ثم **Run workflow** على الفرع `feat/windows-one-click-desktop-package`.
3. اختيار **Windows desktop package** ثم **Run workflow** على الفرع نفسه.
4. لا تُعتبر الحزمة جاهزة حتى ينجح اختبار Python وبناء Windows، بما يشمل تشغيل EXE وفحص الحزمة وSHA-256 ورفع artifact.

لا يلزم إدخال أي كلمة مرور أو DSN لإجراء هذين الاختبارين؛ الاختبارات تستخدم قواعد اختبار وبيانات وهمية.
