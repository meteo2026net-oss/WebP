## 1. القرارات المعتمدة

### 1.1 منصة التشغيل: Desktop

- التطبيق الأساسي برنامج سطح مكتب Windows مستقل.
- تبقى PySide6 الواجهة الأصلية في الإصدار الانتقالي.
- الحزمة المحمولة الحالية أساس التوزيع المؤقت، ويُطوّر لاحقاً مثبت Windows كامل.
- لا يُحوّل المنتج إلى PWA أو موقع ويب بوصفه المنصة الأساسية.
- يمكن إضافة خدمة مساعدة اختيارية للاتصال بقواعد بيانات بعيدة أو للمزامنة، لكن لا تجعلها شرطاً لتشغيل التطبيق المحلي الأساسي.

### 1.2 استراتيجية البيانات: Hybrid

- يدعم المنتج أكثر من اتصال وقاعدة بيانات في الوقت نفسه.
- لكل اتصال ملف تعريف مستقل: النوع، الاسم، المضيف، المنفذ، قاعدة البيانات، المستخدم، TLS/SSL، وحالة الاتصال.
- تحفظ الأسرار في مخزن أسرار نظام التشغيل، ولا تحفظ كلمات المرور كنص صريح في ملفات الإعدادات.
- تُربط النماذج الجوية بمخازن البيانات وفق سياسة توجيه يحددها المستخدم.
- يمكن اختيار قاعدة مركزية وتجميع بيانات محددة فيها، مع بقاء المصادر الأصلية مستقلة.
- المزامنة والتجميع عمليتان صريحتان قابلتان للمراجعة، وليستا نسخاً عشوائياً أو حذفاً للمصدر.

**النطاق الأولي للموصلات:** SQLite وPostgreSQL. إضافة MySQL/MariaDB أو مخازن كائنات سحابية تتطلب موصلات واختبارات مستقلة، ولا تُعد موجودة حالياً لمجرد اعتماد الاستراتيجية الهجينة.

### 1.3 التصميم: Hybrid Meteorology + Data Management

تتكون الواجهة المستهدفة من مساحتين متكاملتين:

1. **مساحة الأرصاد:** المصادر، النماذج، التشغيلات، التنزيلات، GRIB، الخرائط، المقارنة والمراجعة.
2. **مساحة إدارة البيانات:** اتصالات قواعد البيانات، توجيه النماذج، التجميع والمزامنة، التخزين، الصحة، السعة والتقارير.

تُستخدم لوحة رئيسية موحدة، وقائمة تنقل جانبية، وصفحات مستقلة لكل وظيفة. لا تُحشر إعدادات الاتصالات والنسخ الاحتياطي والتنزيلات والخرائط كلها في شاشة واحدة.

## 2. جرد الوضع الحالي كما هو في الفرع المدقق

### 2.1 التقنية وبنية التطبيق

- Python package تحت src/ecmwf_collector/.
- واجهة سطح المكتب مبنية على PySide6.
- نافذة التطبيق الحالية معرفة في src/ecmwf_collector/gui/main_window.py، ويبلغ الملف نحو 1,939 سطراً في الفرع المدقق.
- الواجهة الحالية مبنية أساساً على تبويبات ومجموعات عناصر داخل نافذة واحدة؛ حجم النافذة الابتدائي 1000×860 واتجاهها RTL.
- عارض الخرائط في map_viewer/ مبني على Leaflet ويُقدّم محلياً بواسطة serve_map.py.
- حزمة المعالجة العلمية تشمل ecCodes وcfgrib وxarray وNumPy وSciPy وpyproj وPillow، مع psycopg للاتصال بـ PostgreSQL.
- إصدار CI الخاص ببناء Windows يستخدم Python 3.12 x64 وPyInstaller.

### 2.2 مصادر البيانات والوظائف الموجودة

تتضمن الواجهة والشفرة الحالية:

- WMO Support عبر FTP/FTPS.
- ECMWF Open Data.
- ECMWF ecCharts عبر WMS.
- CPTEC ETA.
- Windy GFS.
- NOAA GFS وNOAA GEFS.
- كتالوج التنبؤات ومساحة مقارنة المصادر.
- مساحة SYNERGIE ومراجعة المتنبئين.
- تبويبات تعريفية لموصلات مستقبلية مثل DWD وUK Met Office وJMA وMétéo-France وCopernicus وEUMETSAT؛ وجود التبويب التعريفي لا يعني أن الموصل مكتمل.

المعالجة الحالية تشمل فحص GRIB، وفهرسة الملفات، وحساب بصمات SHA-256، وتحويل الحقول المدعومة إلى طبقات خرائط، وعرض بيانات النقطة، وإنتاج بعض مخرجات الرياح والتجميعات.

### 2.3 التنزيل والشبكة

الوظائف الموجودة التي يجب الحفاظ عليها وإعادة استخدامها:

- معاينة خطة التنزيل قبل التنفيذ.
- تنزيل متوازٍ من خلال مدير التنزيل؛ حد التوازي الحالي في هذا المسار لا يتجاوز 3.
- ملفات مؤقتة .part واستكمال التنزيل في مسار WMO عند دعم الخادم لذلك.
- تحقق من أحجام الملفات وبنية الملفات وبصمة SHA-256 قبل اعتماد الملف النهائي.
- إيقاف مؤقت/آمن، وإظهار التقدم وعدد الملفات والبايتات.
- معالجة بعض أخطاء الشبكة والمساحة والمصادقة.
- يوجد أيضاً مسار HTTP مستقل للاستكمال باستخدام Range وETag/Last-Modified وإعادة المحاولة بتأخير تصاعدي.

هذه وظائف قائمة في موصلات ومسارات مختلفة؛ لم يثبت التدقيق وجود محرك موحد يطبق سياسة واحدة على كل المصادر. توحيد الجدولة والسرعة وإعادة المحاولة والاستئناف من أهداف التطوير، لا ميزة مكتملة حالياً.

### 2.4 التخزين الحالي ومعنى السجلات الـ570

يوجد حالياً مخزن حالة واحد نشط في كل تشغيل:

- SQLite عبر StateStore.
- أو PostgreSQL عبر PostgresStateStore عند إعداد اتصال PostgreSQL.

المخزنان يطبّقان واجهة سجل الملفات نفسها تقريباً. الجدول الحالي هو files في SQLite أو public.files في PostgreSQL، ومفتاحه الأساسي remote_path.

حقول الجدول الحالية:

- remote_path
- remote_size
- local_path
- status
- local_size
- sha256
- detected_type
- validation
- downloaded_at
- attempts
- last_error
- updated_at

**تفسير العدد 570:** العدد الذي شاهده المستخدم هو عدد صفوف تتبع الملفات في public.files بعد الترحيل. هذه سجلات كتالوج/حالة تنزيل ومسارات وبصمات ونتائج تحقق؛ ليست 570 ملف CSV، وليست 570 حقلاً جوياً أو صفاً من قيم التنبؤ. ملفات GRIB/CSV الأصلية تحفظ كملفات منفصلة في نظام الملفات، ويشير local_path إليها عند توفره.

### 2.5 PostgreSQL الحالي: ما يفعله وما لا يفعله

الموجود حالياً:

- اتصال PostgreSQL اختياري بوصفه بديلاً لمخزن حالة SQLite.
- يُقرأ DSN من متغير البيئة ECMWF_POSTGRES_DSN أو من Windows Credential Manager.
- عملية الربط الحالية تنشئ جدول public.files وتجهز دور تطبيق مخصصاً باسم ecmwf_webp_app بصلاحيات DML محدودة.
- يُنشأ backup لـ SQLite قبل الترحيل، وتتم مقارنة السجلات قبل تبديل المخزن النشط.
- يوجد تشخيص وتثبيت اختياري لـ PostgreSQL عبر winget، ونسخ احتياطي/استعادة.
- يوجد مسار رجوع صريح إلى SQLite عند تعذر فتح PostgreSQL، دون حذف قاعدة SQLite.

غير الموجود بعد:

- لا توجد شاشة عامة لإدارة عدة ملفات تعريف لقواعد البيانات.
- لا توجد قائمة اتصالات متعددة نشطة في الجلسة.
- لا توجد سياسة توجيه تربط كل نموذج جوي بقاعدة مستقلة.
- لا توجد خدمة مزامنة عامة بين قواعد متعددة أو مركز تجميع اختياري.
- لا يثبت وجود موصلات تشغيلية لـ MySQL/MariaDB أو قواعد سحابية متعددة.
- PostgreSQL الحالي يخزن حالة تتبع الملفات؛ لا يعني ذلك أن كل بيانات GRIB أو خلايا الشبكات الجوية تُخزن فيه.

### 2.6 مخطط الطقس الموجود منفصلاً

يوجد ملف sql/weather_platform_schema.sql يتضمن مخطط weather وجداول وصفية مثل النماذج والتشغيلات والشبكات والمتغيرات والمستويات والأصول والحقول ومهام الإدخال والمقارنات والمراجعة. يعتمد جزء الشبكات المكانية على PostGIS.

هذا المخطط يمثل أساساً قائماً لتخزين بيانات الطقس الوصفية والتحليلية، لكنه منفصل عن مخزن حالة التنزيل public.files. لا يجوز وصفه على أنه قاعدة موحدة مكتملة موصولة بكل تبويبات سطح المكتب؛ يجب فحص وتوثيق مسارات الكتابة والقراءة قبل توصيله بمركز البيانات الجديد.

**مبدأ التخزين العلمي:** تحفظ ملفات المصدر الأصلية والبيانات الشبكية الكبيرة في نظام ملفات أو مخزن كائنات/صيغة chunked مناسبة. تحتفظ قاعدة البيانات بالفهرس الوصفي والروابط والبصمات والأحجام والتشغيلات والحقول وحالة المعالجة. لا تُحوّل كل خلية شبكية إلى صف SQL دون مبرر واختبارات أداء.

### 2.7 الحماية والاستعادة

الموجود حالياً:

- تخزين الأسرار عبر keyring/Windows Credential Manager.
- تنقيح بيانات الاعتماد من السجلات ورسائل الواجهة في المسارات التي اختُبرت.
- دور PostgreSQL للتطبيق دون SUPERUSER أو CREATEDB أو CREATEROLE أو BYPASSRLS.
- التحقق من صلاحيات الاتصال والمخطط والجدول عند بدء مخزن PostgreSQL.
- نسخ احتياطي واستعادة مع التحقق من الأرشيف في مسارات PostgreSQL، ونسخ SQLite.
- اختبارات تغطي فشل التهيئة والاستعادة والتراجع وحماية البيانات.

لا تزال هناك حاجة إلى سياسة موحدة لإدارة أسرار اتصالات متعددة، وتدوير كلمات المرور، والتحقق من TLS، ونسخ احتياطي لكل اتصال/مخزن، وتوثيق الاستعادة على جهاز نظيف.

### 2.8 التوزيع والتثبيت

الموجود حالياً:

- بناء Windows x64 باستخدام PyInstaller بنمط onedir.
- حزمة ZIP محمولة تحتوي EXE وملفات التشغيل وSTART.bat وأداة تحقق وبصمات SHA-256.
- الحزمة المحمولة تضم الاعتماديات اللازمة للتطبيق، ولا تتطلب تثبيت Python على جهاز التشغيل.
- أداة التحقق تفحص سلامة الملفات، وتشغيل EXE، ومجلد بيانات المستخدم، وخادم الخرائط المحلي.
- يوجد مسار تثبيت PostgreSQL اختياري عبر winget، لكنه لا يساوي مثبت التطبيق الكامل ولا ينشئ تلقائياً كل قاعدة بيانات يختارها المستخدم.

ما لم يكتمل بعد:

- مثبت Windows تقليدي (مثل MSI أو Setup EXE) بواجهة إعداد.
- فحص شامل لمتطلبات الجهاز والمساحة والصلاحيات والاعتماديات الخارجية.
- تثبيت/تهيئة اختيارية وآمنة للخدمات الخارجية وقواعد البيانات مع موافقة المستخدم.
- ترقية التطبيق مع الحفاظ على مجلد البيانات والإعدادات.
- اختبار تثبيت نظيف على جهاز آخر دون بيئة تطوير.

## 4. الفجوات الرئيسية للإصدار الثاني

1. **طبقة اتصالات:** استبدال DSN وحيد بمدير ملفات تعريف متعدد الاتصالات، مع اختبار الاتصال وتعديل الملف وتعطيله وتحديد دوره.
2. **طبقة محولات قواعد البيانات:** واجهة موحدة للعمليات مع دعم أولي موثق لـ SQLite وPostgreSQL، ومنع افتراض أن كل قواعد البيانات متطابقة.
3. **توجيه النماذج:** سياسة قابلة للتعديل تحدد أين تحفظ بيانات كل مصدر/نموذج/نوع منتج.
4. **مزامنة وتجميع:** مهام ذات معرفات، checkpoints، idempotency، provenance، كشف التكرار والتعارض، وسجل تدقيق؛ مع preview قبل الكتابة.
5. **فصل الملفات عن الفهرس:** واجهة تخزين للملفات المحلية أولاً، ثم مخازن كائنات اختيارية، مع فحص المساحة والحجم والبصمة.
6. **مراقبة البيانات:** عدد الملفات والسجلات، الأحجام، النمو، حالة الاتصال، أخطاء التنزيل والمزامنة، وسلامة الفهارس.
7. **واجهة جديدة:** فصل الشاشة الرئيسية عن مساحات العمل وإزالة التكدس الحالي، مع دعم RTL وتغيير حجم النافذة.
8. **المثبت:** كشف المتطلبات وتحديد ما هو مضمّن وما يحتاج تثبيتاً منفصلاً، مع عدم تثبيت خدمة قاعدة بيانات أو تغييرها بصمت.
9. **ترحيلات قابلة للإصدار:** مخطط migrations مرقم، نسخ احتياطية قبل التغيير، وفحوص رجوع وتوافق.

### قواعد تصميم لا يجوز تجاوزها

- ملف الاتصال يحتوي مرجعاً إلى السر، لا كلمة المرور نفسها.
- لا يُستخدم حساب مدير قاعدة البيانات في عمليات التطبيق اليومية.
- لا يؤدي اختبار الاتصال إلى إنشاء قاعدة أو جدول أو دور تلقائياً.
- لا يؤدي ربط اتصال جديد إلى تبديل المخزن النشط دون معاينة وموافقة ونسخة احتياطية.
- لا تُحذف بيانات المصدر بعد التجميع؛ سياسة الحذف المنفصلة تتطلب موافقة صريحة.
- كل عملية مزامنة قابلة للاستئناف، وتمنع تكرار الكتابة، وتوثق المصدر والهدف والنتيجة.
- لا تُرفع ملفات GRIB/CSV المقيدة إلى Git أو سجل CI أو ملفات تشخيص.
- يجب أن تبقى وظائف WMO وECMWF Open Data وNOAA والتنزيل والمعالجة والخرائط متاحة أثناء إعادة بناء الواجهة.

## 7. خطة حماية البيانات أثناء التطوير

- تُعامل SQLite الحالية وPostgreSQL الحالية كبيانات مستخدم، وليست بيانات اختبار.
- لا تُشغّل اختبارات destructive على قواعد المستخدم الحقيقية.
- تستخدم اختبارات التكامل قواعد مؤقتة/مخصصة قابلة للإزالة.
